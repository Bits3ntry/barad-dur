# BARAD-DÛR Security Workflow (autonomous Trivy runner)

## Specs

S1 (independencia y configurabilidad): "el workflow debe ejecutarse aunque BARAD-DÛR, Dependency-Track o DefectDojo no estén disponibles, salvo cuando la publicación sea expresamente obligatoria." "Configurabilidad: comportamiento controlado mediante un archivo YAML y variables de entorno, sin modificar scripts para cada proyecto." "Implementar un archivo `barad-security.yml` por repositorio" "Implementar validación de esquema con errores claros." "No permitir que los valores controlables desde el repositorio se conviertan en argumentos de shell sin validación." "Las credenciales deben suministrarse exclusivamente mediante variables de entorno o mecanismos de secretos del runner."

S2 (motor Trivy siempre + SBOM condicional): "Trivy realizará todos los análisis de seguridad y generará los SBOM CycloneDX. No integrar inicialmente Syft ni otros generadores." "en cada ejecución del workflow, Trivy debe generar un informe de seguridad JSON." "generar un SBOM si cambian las dependencias, la versión de aplicación, su entorno de construcción o el artefacto; también obligatoriamente en una release."

S3 (regla de decisión): "ALWAYS: run_trivy = true" / "IF dependency_changed OR version_changed OR build_context_changed OR release_event OR initial_inventory_missing: generate_sbom = true" / "Cuando no exista un SHA base fiable, utilizar una estrategia conservadora: generar el SBOM y registrar el motivo `base_reference_unavailable`." "Distinguir expresamente: application_version_changed … dependency_changed … build_context_changed … release_event … initial_inventory_missing". "La comparación debe considerar todos los commits de una PR, no únicamente el último." "En monorepos, limitar la detección al servicio y sus dependencias compartidas relevantes." "El detector no debe asumir que un cambio de código ordinario implica necesariamente una nueva composición de dependencias."

S4 (Trivy: informe y honestidad): "trivy fs . --scanners vuln,secret,misconfig --format json --exit-code 0 --output trivy-report.json" "No considerar `0 findings` equivalente a `scan successful` sin comprobar que Trivy terminó correctamente." "Si se detectan secretos, producir versiones sanitizadas de las evidencias que se envíen a BARAD-DÛR o se conserven fuera del runner." "No almacenar indiscriminadamente archivos encontrados ni valores de credenciales." "Un finding de Trivy no debe hacer fallar automáticamente el workflow. Un fallo técnico real sí debe identificarse correctamente." "No mezclar errores técnicos con hallazgos de seguridad." "No tratar ausencia de findings como prueba de seguridad."

S5 (SBOM CycloneDX): "trivy fs . --format cyclonedx --output sbom.cdx.json" "Comprobar, como mínimo: `bomFormat = CycloneDX`. Versión de especificación. Lista de componentes. Componentes con PURL. Relaciones de dependencias, cuando existan. Metadatos del generador. Fecha y contexto de generación." "No inventar relaciones ausentes. Si Trivy no genera un grafo suficiente para Dependency-Track, registrar una advertencia sobre la calidad del SBOM." "El SBOM no debe incluir automáticamente resultados de vulnerabilidades".

S6 (evidencias y manifiesto): "Cada ejecución debe dejar un registro completo y estructurado, incluso si Trivy falla o una publicación no se completa." "Implementar: Identificador único por ejecución. Timestamps UTC. Identificador del servicio. SHA de commit. Referencia de PR, cuando exista. Entorno de ejecución. Versión y configuración efectiva de Trivy, sin secretos. Motivos de ejecución y omisión de cada etapa. Tiempos por etapa. Contadores por tipo y severidad. Errores técnicos diferenciados de hallazgos de seguridad. Checksums SHA-256 de evidencias. Estado de publicación de cada integración. Identificadores devueltos por los sistemas externos. Trazabilidad de reintentos." "Utilizar estados diferenciados como: PENDING RUNNING SUCCESS FAILED SKIPPED PARTIAL" "Un resultado de seguridad con vulnerabilidades detectadas puede seguir teniendo estado técnico `SUCCESS`."

S7 (ciclo de vida SBOM / Dependency-Track): "No crear proyectos permanentes en Dependency-Track." (PR) "No crear un proyecto nuevo por cada commit." (main) "No sobrescribir el inventario de una release histórica con un SBOM procedente de código más reciente." "Si la misma versión publicada recibe un nuevo SBOM, comprobar si representa una reimportación idéntica, una corrección de inventario o una reconstrucción distinta. Registrar esta situación y no modificar silenciosamente el histórico." "No marcar automáticamente `main` como `Latest`." "Evitar crear duplicados por repetición de una misma ejecución." "No crear proyectos de Dependency-Track por cada PR."

S8 (BARAD-DÛR opcional y sincronización): "POST /api/v1/security-runs" "POST /api/v1/security-runs/{id}/artifacts" "POST /api/v1/security-runs/{id}/complete" "Estos endpoints son un contrato propuesto: no asumir que ya existen." "Si BARAD-DÛR no responde, el workflow debe conservar los artefactos y registrar `publication_pending` o `publication_failed`, sin perder el resultado del análisis." "barad-security sync --run-id RUN_ID" "La sincronización no debe repetir automáticamente un escaneo ya completado."

S9 (DefectDojo opcional): "Implementar un adaptador opcional que permita enviar los informes JSON de Trivy." "No importar informes de PR por defecto." "No convertir automáticamente todos los hallazgos de Trivy en tareas de remediación." "Distinguir importación de evidencias y clasificación de findings accionables."

S10 (portabilidad y CI): "barad-security run --event pr" "barad-security run --event release --version 8.9.0" "barad-security sync --pending" "Local: CLI directamente. Hook de Git opcional con Husky. `act` para validar el workflow de GitHub Actions." "Reusable workflow mediante `workflow_call`." "La lógica de seguridad debe permanecer en el runner común." "Los hooks locales no deben generar una segunda implementación de análisis." "Las llamadas que requieren secretos deben ejecutarse exclusivamente en contextos autorizados; no exponer credenciales a PR de forks o código no confiable."

S11 (logs): "Implementar logs estructurados, preferiblemente JSON Lines" "También debe existir una salida legible en terminal." "Los errores en publicaciones opcionales no deben ocultar los resultados de análisis."

S12 (pruebas): "Los tests unitarios no deben depender de APIs externas. Utilizar mocks o fixtures." "Añadir una prueba end-to-end local real con Trivy instalado." "No finalizar únicamente con documentación: dejar los escenarios ejecutables y verificados." "Antes de dar la implementación por terminada, ejecutar los tests, validar al menos un análisis real con Trivy y documentar cualquier limitación o integración externa no verificada."

S13 (escenarios de aceptación): "Escenario 1 — Cambio de código … Trivy se ejecuta, el SBOM no se regenera y se conserva un manifiesto que explica la decisión." "Escenario 2 — Cambio de dependencia … Trivy se ejecuta, genera un nuevo SBOM, registra los cambios y conserva ambos informes vinculados al commit." "Escenario 3 — Nueva release … lo publica en `OVAC-Backend 8.9.0` de Dependency-Track." "Escenario 4 — Integración con BARAD-DÛR caída … se conservan todos los informes y la ejecución queda pendiente de sincronización, sin perder información." "Escenario 5 — Migración a GitHub … utiliza el mismo motor y configuración que en local, genera el mismo contrato de evidencias y publica utilizando secretos de GitHub."

S14 (reglas de implementación): "No sustituir el workflow por una simulación de resultados." "No inventar vulnerabilidades, estados o ejecuciones." "No desarrollar un escáner propio." "No utilizar una base de datos persistente si no es necesaria para el runner." "No crear proyectos de Dependency-Track por cada PR." "No generar tickets de DefectDojo por cada CVE sin una decisión explícita." "Puedes elegir Python o Node.js para implementar la CLI, justificando la decisión."
