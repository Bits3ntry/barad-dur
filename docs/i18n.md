# Translations (i18n)

The console speaks more than one language without a second code base: every
string a person reads comes from a JSON catalogue, and the language is a folder.

## How it works

```
frontend/src/i18n/index.jsx          provider, t(), tCount(), tOr(), storage, <html lang>
frontend/src/i18n/locales/en/*.json  source of truth (English)
frontend/src/i18n/locales/es/*.json  Spanish
frontend/src/i18n/locales/<xx>/*.json any other language — discovered at build time
```

`import.meta.glob` merges every namespace of every language at build time, so the
catalogues ship inside the bundle and a language switch is a React state change,
not a request. The choice is stored in `localStorage['barad.lang']`, applied to
`document.documentElement.lang`, and defaults to the browser's language when that
catalogue exists.

Resolution order for a key: **active language → English → the key itself**. A raw
key visible on screen is a bug you can read; an empty string would hide it.

| Helper | Use |
|---|---|
| `t('key')` | a string |
| `t('key', { n: 3 })` | a string with `{n}` placeholders |
| `tCount('key', 3)` | plurals: the catalogue holds `key.one` and `key.other` |
| `tOr('status.' + value, value)` | **data**, not copy: if the catalogue has no name for that value, print the value |

## Adding a language

1. `cp -r frontend/src/i18n/locales/en frontend/src/i18n/locales/pt`
2. Translate the values. Keys, `{placeholders}` and `.one`/`.other` suffixes stay
   byte-identical.
3. Optionally translate the guide: `cp -r frontend/src/guide/en frontend/src/guide/pt`
   and translate the prose (code fences stay as they are).

Nothing else. The selector lists whatever folders exist; a language with no
display name falls back to its uppercase code. A language whose guide is missing
chapters shows the English body with a note, never a blank page.

## Where a key lives

One namespace per area, one prefix per screen inside it. A key names the element,
not the sentence: `findings.empty.title`, `builder.trigger.push`,
`orchestration.kpi.workersAlive`.

| Namespace | Owns |
|---|---|
| `common.json` | primitives in `ui.jsx`, statuses, severities, units, chart labels |
| `nav.json` | sidebar, groups, screen titles, shell (search, theme, sign out) |
| `settings.json` | Settings screen and its panels (security, advisories, mail, runtime) |
| `onboarding.json` | sign-in, first-run walk-through, invitation, terminal approval |
| `projects.json` | projects, portfolio, verification |
| `findings.json` | findings, my work, vulnerabilities, exposures, analysis |
| `builds.json` | builds/SBOM, components, licenses, code review |
| `cycle.json` | dashboard, CTEM overview, cycles, business impact, lifecycle |
| `governance.json` | grants, members, audit, notifications, setup guide |
| `runs.json` | orchestration, surface run, scan dialog |
| `delivery.json` | pipelines, pipeline builder, gates, regression, pentests |
| `ai.json` | chat, assistant, AI runs, missions, AI settings |
| `surface.json` | assets, asset detail, attack surface, scope, Jira |
| `graphs.json` | graph/diagram components and the release dialog |
| `guide.json` | the in-product guide's chrome (chapter labels, doors, search) |

## Which Spanish

The Spanish catalogue is **peninsular Spanish (`es-ES`)**, not Rioplatense: `tú`
forms ("elige", "añade", "abre", "prueba"), "aquí/allí" rather than "acá/allá",
and the technical vocabulary the Spanish console uses ("escaneo", "ejecución",
"hallazgo", "autorización", "responsable"). The document declares `es-ES`, so
browser hyphenation and screen readers agree with the copy. A translation written
in another variant is a defect, not a variation: keep one Spanish per catalogue.

## What is never translated

- **Data**: package names, purls, CVE/KEK/GHSA ids, hostnames, IPs, emails,
  commit shas, file paths, counts, dates, user names. They are printed as they
  arrive.
- **Identifiers**: profile ids (`recon.simple`), capability ids (`validate`),
  API enum values (`push`, `pull_request`), env var names, HTTP paths, code.
- **Brands**: barad-dûr, Shauron, Jira, Slack, GitHub, Palantír, Angmar, Morgoth.
- **Things a form submits**: translating a value that is later sent to the API
  changes stored data. Translate the label, never the payload.

## The check

```sh
npm run i18n --prefix frontend
```

It fails the build (exit 1) when:

- a language's key set differs from English (missing or extra), because a missing
  key silently renders English inside a Spanish screen;
- a key is defined twice across namespaces;
- a `t('…')` literal used in code does not exist.

It reports, without failing:

- files that still hold hardcoded prose (the migration's to-do list);
- keys defined and not used yet.

## Adding a string to a screen

1. `const { t } = useI18n()` as the **first** statement of the component.
2. Replace the literal with `t('namespace.key')`; keep the English text identical.
3. Add the key to `locales/en/<namespace>.json` and the translation to `es/…`.
4. `npm run i18n --prefix frontend` and `npm run build --prefix frontend`.

Module-level tables (`const STEPS = […]`) keep their shape and carry
`labelKey`/`hintKey` fields resolved with `t()` where they render — never a
translated string stored in a constant, because a constant is evaluated once and
would freeze the language it was first rendered in.

## Known limits

- The API answers in English (error details, audit actions, model output). Those
  strings are shown as they arrive; translating the backend is a separate job.
- Dates printed with `toLocaleString()` follow the browser, not the chosen
  language, on the screens that were not migrated to the hook's `date()` helper.
- The guide is prose in `frontend/src/guide/<lang>/`; a chapter translated into a
  new language appears automatically, and an untranslated one says so.
