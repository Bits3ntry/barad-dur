# Plan: bajar el coste y la latencia de la IA sin perder respuestas

> **Estado: ejecutado (2026-11-09).** Medido después del deploy, dos corridas por
> pregunta: findings 18.144/40.012 → **10.113/10.872** (−64 %), node2shell 8.856 → **6.291**
> (−29 %), proyectos 3.770 → 3.771 (sin cambio: no tenía desperdicio). Varianza de la
> misma pregunta: **120 % → 7,5 %**. Golden set **4/4** antes y después. `cached_tokens`
> del proveedor: 3.072 de 106.904 tokens de entrada, antes invisible.

**Goal.** Reducir ≥50 % los tokens de entrada por run y la latencia percibida, midiendo
antes y después, sin bajar la tasa de respuestas correctas.

## Contexto actual (medido, no estimado)

Medido contra la base viva el 2026-11-09:

```
por rol:  estate.inventory | 46 steps | avg_in 3983 | avg_out 545 | max_in 16564
runs:     17 totales | 14 answered | 2 stopped | media 12.251 tokens
top run:  3 steps | 26.814 in | 1.931 out | 18 s
ratio:    in:out ≈ 10:1  → el coste está en la ENTRADA, no en la respuesta
```

La causa está localizada, no es una hipótesis:

- `backend/src/backend/app/ai/orchestrator.py:240` mete el resultado de cada tool en
  `messages` como `role: "tool"` con `projection(payload)`, y
  `backend/src/backend/app/ai/state.py:42` permite hasta **`MAX_TOOL_CHARS = 12000`**.
- El loop reenvía **todo el historial** en cada llamada (`engine.complete(provider, api_key, messages, ...)`,
  `orchestrator.py:186`). Con 2 tool results grandes, el step 3 paga otra vez los 12 k del
  step 2: crecimiento cuadrático.
- No se registra caché del proveedor: `engine.complete` sólo lee `usage.prompt_tokens` y
  `usage.completion_tokens`, así que un acierto de caché es invisible.
- No hay presupuesto por run: `engine.budget_check` (línea ~166) sólo mira el **cap
  mensual**.
- El chat es bloqueante: `frontend/src/Chat.jsx:67` hace `await api.post('/turns')` y no
  muestra nada hasta que el run termina (18–34 s medidos).

Ya existe y **no hay que reinventar**: `state.projection()` (muestreo + truncado),
`state.summary()` (`MAX_SUMMARY_CHARS = 6000`), `session.assemble()` (brief + pins +
`K_TURNS = 6`), `ANSWER_NOW` en el último step y el ledger `AiStep`.

## Arquitectura del cambio

Tres cortes sobre el mismo loop, en este orden: **medir** (caché y baseline), **recortar
la entrada** (tool results por step, resumen más corto, dedupe de llamadas), y **mejorar
la percepción** (progreso en vivo en el chat, coste visible por sesión). No se toca el
planeador ni el contrato de herramientas.

## Principio: recortar la repetición, no la capacidad

Una optimización que reduce lo que el modelo **puede** hacer no es una optimización, es
un recorte de producto con mejor factura. Cinco reglas que ninguna tarea puede violar:

1. **El modelo conserva acceso a todo.** `brief_result` es un puntero, no una censura:
   declara qué se omitió y la tool se puede volver a pedir (T5 la cachea, no la bloquea).
   El raw sigue en `run_state` y en el artefacto.
2. **El presupuesto es un guardarraíl, no una cuota.** `NULL` por defecto; cuando existe,
   es por perfil y generoso (60k/200k/400k). Al agotarse, el run termina
   `stopped_budget` **con lo encontrado**, igual que `budget_exhausted`.
3. **No se recorta la salida.** El ratio es 10:1 hacia la entrada: bajar `max_output_tokens`
   ahorra calderilla y es exactamente dónde se nota la pérdida de calidad.
4. **No se cambia el modelo a uno más tonto** para ahorrar. Si algún día se usa uno barato,
   será para planificar, y la redacción seguirá en el grande.
5. **La capacidad se mide, no se supone.** Un golden set de preguntas con respuesta
   esperada (T11); si una respuesta empeora, se revierte la tarea que la empeoró, aunque
   haya bajado los tokens.

La regla mental: **si el cambio hace que el modelo sepa menos, está mal; si hace que pague
menos por saber lo mismo, está bien.**

Usage: .venv/bin/python backend/scripts/ai_cost_baseline.py <api-key>

import json

import sys
import urllib.request

QUESTIONS = [
    "¿cuántos findings abiertos tengo?",
    "¿nos afecta node2shell?",
    "¿qué proyectos hay?",

def call(path: str, key: str, payload: dict | None = None) -> dict:
    url = os.environ.get("PLATFORM_URL", "http://127.0.0.1:8090") + path
    data = json.dumps(payload).encode() if payload else None

                          "steps": body.get("steps"),
                          "tokens_in": body.get("tokens_in"),
                          "tokens_out": body.get("tokens_out")}, ensure_ascii=False))
    return 0

"""The canonical question must cost a fraction of what it cost before the change.

The baseline is measured, not invented: T1 prints it and it is committed next to this

"""
import json
import os
from pathlib import Path

import pytest

BASELINE_PATH = Path(__file__).with_name("ai_budget_baseline.json")
FACTOR = float(os.environ.get("AI_BUDGET_FACTOR", "0.6"))


def _baseline() -> dict:
    return json.loads(BASELINE_PATH.read_text())


@pytest.mark.skipif(not os.environ.get("AI_BUDGET_KEY"),
                    reason="needs a live provider key (set AI_BUDGET_KEY)")
def test_the_canonical_questions_cost_a_fraction_of_the_baseline(client):
    baseline = _baseline()
    for question, before in baseline.items():
        body = client.post(
            "/api/v1/ai/runs",
            headers={"X-API-Key": os.environ["AI_BUDGET_KEY"]},
            json={"question": question, "mode": "ask"}).json()
        run = body.get("data") or body
        total = (run["tokens_in"] or 0) + (run["tokens_out"] or 0)
        assert total <= before * FACTOR, (
            f"{question!r}: {total} tokens, baseline {before}, "
            f"allowed {int(before * FACTOR)}")

## Riesgos y decisiones abiertas

- **La capacidad es la puerta, no los tokens.** Si T11 baja de 4/4, se revierte la
  tarea que lo causó aunque el ahorro sea grande. Optimizar es pagar menos por lo mismo.
- **Recortar el tool result puede costar recall.** Mitigación: `brief_result` declara
  cuántas filas se omitieron y cómo volver a pedirlas; el test de regresión de respuesta
  (`test_ai_orchestration.py`) debe seguir verde. Si un caso necesita el raw, el modelo
  puede repetir la llamada — por eso T5 cachea el resultado en vez de impedirla.
- **`MAX_TOOL_CHARS = 4000` es un cambio de comportamiento, no un tuning.** Debe ir con
  el test de T3 y con una corrida de las tres preguntas canónicas en el mismo commit.
- **El caché del proveedor es opcional.** `prompt_tokens_details.cached_tokens` no lo
  devuelven todos; si `opencode-go` no lo envía, la columna quedará en 0 y eso también es
  información (dice que no hay ahorro por caché en ese plan).
- **Modelo por fase** (barato para planificar, grande para redactar) queda fuera a
  propósito: añade una variable al mismo tiempo que estamos midiendo otra. Se decide
  cuando T1–T10 estén desplegados y con datos.
- **SSE vs polling.** Polling cada 1 s es suficiente para 20 s de espera y no cambia el
  contrato HTTP. SSE se justifica cuando el turno pase de 60 s o haya varios runs
  concurrentes por sesión.
