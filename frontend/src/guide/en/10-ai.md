The AI layer reads what the platform already knows and proposes work. It does not replace a scanner, and its prose is never evidence.

The division, which every other rule follows from: **the platform keeps the provider key, the budget, the plan and the triage gate; Shauron keeps the tools, the sandbox and the network position.**

### Configure a provider

Settings → **AI** has one provider list, one budget and one meter.

| Field | Notes |
|---|---|
| kind | `openai-compatible` covers OpenAI, OpenRouter, Ollama, vLLM and most others. Anthropic is listed and not implemented yet |
| name | yours: `deepseek`, `local-llama` |
| base URL | for a local runtime on the host: `http://host.docker.internal:11434/v1` |
| model | free text with suggestions — vendors rename models faster than any list survives |
| key | write-only and sealed; it is never returned by the API. A keyless local runtime needs none |
| price in / out per 1M | empty means *unknown*, not free |
| max output tokens | per call |

Two counters sit beside the providers: a **monthly token cap** and a **monthly cost cap**. A run that reaches one stops **before** its next model call and stays visible as `stopped_budget`, with the cap named. That is the difference between a budget and a surprise invoice.

A provider can be disabled without deleting it — disabling keeps the row and its history, deleting removes the credential. Prefer disabling when you are debugging.

### The three profiles

A profile is a promise about what the system will **not** do.

| Profile | Tagline | Lane | Sees | Budget | Level cap |
|---|---|---|---|---|---|
| **Palantír** | the seeing stone: answers from what the estate already knows | none (read-only) | components, builds, deployments, assets, observations, findings, scope, grants, intel | 6 steps / 30k tokens | 2 |
| **Angmar** | the blade: reproduce a documented finding, or dismiss it | `validate` | the finding, its evidence, its target's scope | 20 steps / 60k tokens | 3 |
| **Morgoth** | the hunter: it wants vulnerabilities, not tickets | `discover`, `exploit` | everything Palantír sees, plus technology, endpoints, rejected hypotheses, signature coverage | 40 steps / 400k tokens | 4 |

**Palantír never gets a field task.** It answers questions from rows the platform holds, cites them, and says *unknown* with the missing edge when the estate cannot answer. Both field profiles require a **plan review** before executing, and `exploit` additionally requires the red-team switch in Settings → AI **and** a grant. A profile is not a mode the operator can talk their way out of.

### Chat

**Chat** is Palantír with a box under it: ask about a component, a build, a finding, an asset or the estate as a whole, and the answer comes from the platform's own data with the rows named. `@profile` addresses a specific profile; Palantír is the one that answers today.

The turn runs **off the request**: the screen gets the run id immediately and reads the answer when the run closes, so a five-specialist chain never leaves you staring at a spinner. Under every answer sit the **ids it read** — each one a door into the console — and a link to **the run**, which is the receipt: steps, tool calls, tokens, and where it stopped. A pin (📌) keeps a turn in the prompt when the conversation is compacted.

The screen has two readings of the same conversation: **conversation** (what was said) and **relations** (who asked whom for what). The second is a projection, not a second record — the orchestrator delegating to a specialist, each handoff with its claims, the field agent running a tool, and every refusal with the reason it gave.

Use it for the question you would otherwise answer with three screens — "which of our builds still carry this library", "what did we observe on this host last week". Do not use it to decide the severity of a finding: that is a decision with a record attached, and it belongs on the finding.

### Prompts, as versions

Each participant — the five specialists and the field loop (`field.generic`) — has instructions you can read and change. The text in code is the **floor**: with no rows, the answer is exactly what the code says (`intel.cve@code`). Saving writes a **draft**, and a draft never reaches a run until somebody activates it; activating archives the previous version instead of deleting it, and every step records which version produced it (`intel.cve@3`), so "what was it told" is a fact and not a memory.

The editor shows what each version actually did: runs, steps, tokens and invalid refs, read from the ledger. That is what turns an edit into a measurement.

The field agent's instructions are injected by the platform in `POST /agent/llm/complete`, so changing them needs no new image in the scanner.

### AI runs

**AI runs** is the ledger: one row per model-backed execution with its steps, tokens, cost, status and the question it was answering. It exists so "the AI said so" never has to be taken on faith — you can see which run, with which profile, on which rows, at what cost, and where it stopped.

### Missions

A **mission** is bounded work with a budget, not an agent you leave running.

Creating one asks for five things:

| Field | Meaning |
|---|---|
| goal | one sentence: *reproduce finding f-1 (SQLi in /api/search)* |
| capability | `validate` (reproduce a documented finding), `discover` (surface recon), `exploit` (prove impact — needs a grant) |
| targets | what it may touch, with the scope the grant covers |
| tools | the allowlist it may choose from |
| budget | tokens, steps, USD, wall-clock minutes |

The mission is then split into **tasks**, each with a typed `must_return`. A field agent claims one task, works inside the envelope, posts events, and exits when the schema is satisfied or the budget is gone. Revoking the mission is the kill switch: it ends the lane and the agent's next call fails.

The capability word maps to the engine's capabilities through one table (`validate`, `discover`, `exploit` are the profile's language; `active_verification`, `code_analysis`, `passive_discovery`, `intrusive_testing` are the engine's). That translation happens in one place on purpose: a silent fallback would hand a capability to a lane nobody granted.

### The tool gateway and MCP

The platform declares its tools once, and that catalogue is shared by the in-process executor and by the **MCP server** in `mcp/` (`barad-mcp`), which exposes the same catalogue to external agents. It installs the platform package next to itself — the catalogue is imported, never copied — and authenticates with a platform identity.

An MCP caller inherits its own principal. It is not a second way to be an owner.

### Five invariants

1. **An AI run inherits the human principal and never escalates.** A service key is an owner credential, so any machine-facing surface ships its own curated allowlist instead of assuming a role check protects it.
2. **A scan must cite the evidence gap it closes.** The tower's own data answers first; the model asks for a scan only when a question cannot be resolved from rows.
3. **Scope is enforced by the absence of a route, not by a prompt.** The agent container has no path to anything but the scope proxy.
4. **Specialists are short-lived typed tasks, not long-lived agents.** That is what keeps context from turning into a rabbit hole.
5. **The model's text is never evidence.** A finding closes with an artefact and a person's decision.

### What the AI layer will not do

It will not invent a host, a version or a CVE, and it will not answer "you are clean" from an empty table — an empty table is a question. If an answer looks confident about something the platform does not hold, that is a defect worth reporting, not a feature.
